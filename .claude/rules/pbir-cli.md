# pbir CLI — project learnings

- Native slicers cannot *receive* cross-filter selections, so "clicking a map bubble should check the city in the slicer" is impossible with a slicer. Replacement: a single-column `tableEx` bound to the same column — rows are click-selectable (filters the page like the slicer did) and a map-click visibly collapses the list to that city. `pbir schema roles tableEx` shows one role, `Values`, which accepts a lone Column. Note `tableEx > columnHeaders` has no `show` property, so the header row cannot be hidden; repurpose it as the caption via `pbir fields rename` (report-wide display name, so every visual using that field relabels).
- `pbir add visual`/`visuals position` refuse placement that overlaps an existing visual. The sidebar backdrop here is a full-height `basicShape` (x24 y72 312x624, z=0) that all left-rail visuals are deliberately layered over, so `--force` is the correct resolution for anything placed in that rail — not repositioning.
- `pbir pages interactions "<Page>" --source X --target Y --type DataFilter|HighlightFilter|NoFilter|Default` DOES author `visualInteractions` (page.json). Default/no entry already gives cross-filtering between visuals over the same table on this relationship-less push dataset.
- `pbir` (v0.9.29) cannot author an arbitrary relative-date window: `add filter --period` is a fixed enum (Last7Days, Last14Days, Last30Days, Last3Months, Last6Months, Last12Months, LastYear) with no Last3Days, no arbitrary N, and no include-today flag; `filterConfig` is unreachable via `pbir get/set` ("Unknown component: filterConfig") even though `pbir filters list` enumerates it. A 3-day "include today" window must be authored in Desktop (calendar-day semantics; pbir's `DateAdd(-N, Now())` windows are rolling-hour anyway).
- A slicer's "default selection" must NOT be a visual-level filter: a Categorical filter in `filterConfig.filters` on the slicer restricts the slicer's own item list (a Units[unit]='Metric' filter made the toggle render only one "Metric" tile, regardless of size/responsive settings). Desktop persists slicer selections under `objects.general.properties.filter` instead (see `pbir-format` skill `examples/visuals/formatted/slicer-flash.json`), which `pbir` (v0.9.29) cannot set. Fix: `pbir rm ".../slicer.Visual/filter:<name>" -f` and rely on the measures' `SELECTEDVALUE(..., "Metric")` fallback for the default.
- `pbir download "<local>.Report" -o <dir>` fetches the linked published copy alongside — diffing it against the local `definition/` is the reliable way to check whether local changes are actually live (they were byte-identical here while the bug persisted, ruling out a stale publish).

- Bare `pbir ls` fails here with `'meteolens.Report' not found`: the `.pbir/active` context file points at a stale name. Always pass the explicit report path (`e89d7c20-65af-95c3-4838-2b659bafdddf.Report`, run from `powerbi/`).
- `pbir model -q` (live DAX execution) cannot work against this report: the dataset lives in the personal "My workspace", and the command resolves workspaces through Fabric Group APIs, which return 401 `GroupNotAccessible` for personal workspaces. `pbir model -d` (schema fetch) uses a different path and works fine.
  - Workaround for DAX probes: POST the query to `https://api.powerbi.com/v1.0/myorg/datasets/<datasetId>/executeQueries` with an `az account get-access-token --resource https://analysis.windows.net/powerbi/api` bearer token. Query must start with `EVALUATE`. Read-only probes only — report mutations still go through `pbir`.
- Push datasets reject `relationships` in the REST create-dataset body (HTTP 400): disconnected tables only. Map coordinates therefore come from SWITCH extension measures over `RealTimeData[location]`, not a related Cities table.
- macOS: `pbir desktop` bridge is unavailable by design; verification is `pbir validate --all` + publish (with consent) + browser check.
- CLI bug (v0.9.29): every filter-enumeration command (`filters list`, `rm .../filter:X`, `filters set/rename`) crashes with "Invalid field reference" on any visual holding a Desktop-authored Advanced filter whose Aggregation-wrapped field lacks a `displayName` — the crash happens during enumeration, so such filters cannot be removed at all. Workaround: rebuild the visual via `pbir cp` from a clean sibling and rebind (stale filters simply aren't carried from a clean source; note `cp` DOES copy the source's filters, so the source must be clean).
- `pbir validate --all` falsely reports measures bound only through `<prop>.cf` (measure-driven titles, background color CF) as UNUSED_EXTENSION_MEASURE — its usage scanner doesn't look inside CF bindings. Verify with `pbir get "<visual>.<prop>.cf"` before believing it.
- altText is a top-level visualContainer field in PBIR that `pbir` (v0.9.29) cannot address via `set` dot-paths or any dedicated command — accessibility alt text currently can't be set through the CLI.
- Extension measures must NOT reference other extension measures on this report (thin report on a push dataset): the service's visual queries omit the referenced measure's DEFINE, so every dependent measure fails at render with "The value for '<measure>' cannot be determined. Either the column doesn't exist, or there is no current row for this column" — even though the same DAX works via `executeQueries` with both DEFINEs present, and `pbir validate` passes. Inline the shared expression (e.g. `SELECTEDVALUE('Units'[unit], "Metric")`) into each dependent measure instead of factoring it out.
- Slicer `data.mode = 'HorizontalList'` (valid in the pbir catalog) is ignored by the service renderer — the slicer falls back to a vertical radio list and extra items get clipped by the visual height. Use the Desktop-native combo instead: `data.mode = 'Basic'` + `general.orientation = 1` for a horizontal tile slicer.
- A horizontal tile slicer also needs `general.responsive = false`. Left at its default (true), the slicer collapses under a small container and renders only the first tile — a two-value Metric/Imperial toggle at 200x48 showed just one "Metric" tile with no second option to click, which looks exactly like "the toggle does nothing". Give it real room too (280x56 works for two tiles). Reference shape: `pbir-format` skill, `examples/visuals/formatted/slicer-flash.json`.
- `pbir` writes every numeric literal in Double form (`1D`, `12D`) even for enum-typed properties like `general.orientation`. That is what Desktop produces as well, so `"Value": "1D"` is correct and not the cause of a mis-rendering enum — don't chase it.
- Narrow cards (184px) overflow their box when the title is a long measure-driven string ("Avg. Cloud Cover (%)"). Cards do not wrap titles by default: set `title.titleWrap = true` plus a smaller `title.fontSize` (11 fits two lines at 184px).
- The service persists each viewer's filter/slicer state and re-applies it OVER the published definition (report.json `settings` lacks `isPersistentUserStateDisabled`). A bad visual filter seen once by a viewer survives every republish for that viewer — local-vs-download diffs being byte-identical proves nothing about what they see. Symptom here: slicer stuck on one "Metric" tile after the filter was removed and republished. Fix: viewer clicks **Reset to default** in the report action bar; prevention: set `isPersistentUserStateDisabled: true`. Console stack `toggleItemSelection → persistSelectionFilter` confirms the mechanism; `dc.services.visualstudio.com ERR_BLOCKED_BY_CLIENT` console errors are just ad-blocked telemetry, not a report problem.
- `cardVisual > border` has no `radius` property in the catalog (only color/show/style/transparency/width) — rounded KPI-card corners cannot be set; `pbir set` rejects it explicitly.
- After a `pbir publish` → `pbir download` round-trip the service reformats the JSON (key order/whitespace), so raw byte diffs show every file "differing" even when content is identical. Compare semantically: `diff <(python3 -m json.tool --sort-keys local) <(python3 -m json.tool --sort-keys downloaded)`. Byte-identity remains meaningful only as proof that nothing changed (the original stale-publish check), not the reverse.
- `pbir publish` targets whatever service report the local folder is *linked* to (the "Using active connection" line) — here that is `meteolens-v2` (`81f29b1c-…`, JHammoFabric), NOT the production `meteolens` report (`7e2b2826-…`), which is kept as rollback and still carries the Desktop-authored `unit_toggle` default-selection that pbir cannot recreate. Never re-link + publish over `meteolens.Report` without explicit consent.
- Renaming a service report: the powerbi.com `PATCH /reports/<id>` endpoint 404s; use the Fabric items API instead — `PATCH https://api.fabric.microsoft.com/v1/workspaces/<ws>/items/<reportId>` with `{"displayName": "..."}` and an `az` token for resource `https://api.fabric.microsoft.com`.
- **`pbir publish`/`download` follow the folder's saved link, and here the link pointed at a stray GUID-named report** (`e89d7c20-…`, id `35438956-c5b1-404a-aba2-baf1dcd4a768`, JHammoFabric) — NOT `meteolens-v2`. A destination-less publish "succeeded" there, and the standard local-vs-download diff then "verified" the same wrong report, so everything looked live while `meteolens-v2` stayed stale. Always pass the explicit destination (`pbir publish "<local>.Report" "JHammoFabric.Workspace/meteolens-v2.Report" -f`) and verify against the target report **id** (Fabric `getDefinition`), never against "the linked copy".
- On macOS the true rendering check is the Power BI **ExportTo API** (PDF; PNG export is tenant-disabled): POST `/groups/<ws>/reports/<id>/ExportTo {"format":"PDF"}`, poll `exports/<exportId>`, download `…/file`, convert with `sips -s format png`. It renders a fresh server-side session of the *specified report id* — the only check that caught the wrong-report publish above (definition diffs cannot).
- `cardVisual` `label`/`value` are **instance-selector objects**: a general-scope `objects.label.show=false` validates and publishes but the renderer ignores it (the field-name label kept rendering). Use the selector mini-language: `pbir set "<Visual>.label.id(default).show" --value false`. Glob patterns (`*.Visual.label.id(default).show`) do not match selector paths — apply per visual.
- Report-extension measure names must be unique against **column** names **model-wide and case-insensitively**, not just against other measures: a measure named `Precipitation` errored against column `RealTimeData[precipitation]`, and `City` errored against `Cities[city]` — a *different table*. Desktop shows "The name 'x' is already used for a column on table 'Y'" per affected visual; `executeQueries` with query-scope `DEFINE MEASURE` does NOT catch this (it allows shadowing), so probe-passing names can still fail in the report. Fix: rename the measure (`Precip Avg`, `Selected City`) and carry the desired label via the projection's `displayName`.
- Chart `dataPoint.fill` **value-driven CF silently fails with a `metadata` selector** — the service ignores the binding and renders theme-default blue (no error, validate passes). `selector.metadata` is only for *static* per-series colors. Value-driven fill CF needs `"selector": {"data":[{"dataViewWildcard":{"matchingOption":1}}]}` (or no selector). Verified 2026-08-19 on `aqi_trend`: a measure-bound fill kept the old `metadata: "RealTimeData.AQI Avg"` selector and every bar stayed blue until the selector was swapped. Prefer rules-based `Conditional.Cases` (PascalCase keys, `ComparisonKind` 4 = `<=`, first match wins, `DefaultValue` fallback) referencing a measure *already projected in the visual's query* — that also sidesteps the extension-measure DEFINE-omission class of failure entirely, and needs no extra color measure.
- Publishing without `pbir` (e.g. the Windows box, which has no pbir/npm/python): the Fabric REST API does the whole loop — `POST /v1/workspaces/<ws>/items/<reportId>/updateDefinition` with all local files as InlineBase64 parts (exclude `.platform` and `.pbi/`; forward-slash paths; 202 → poll the Location header), `getDefinition` to verify the target's live content, then the ExportTo-PDF render check. Same explicit-destination rule applies: meteolens-v2 is `81f29b1c-7758-498c-a367-bb00ac6e9c8a` in workspace `7a102e5b-56e2-4dbc-b04c-5cedff7c3b0e`; production `meteolens` (`7e2b2826-…`) stays untouched.
